# A machine-translation chain behind the Translation Field

Wiktionary's page is the primary source for the Translation Field, but it carries no equivalent for a good share of the headwords a reader actually selects: technical terms, names, recent coinages, and anything whose editors have not written a Translations block yet. Three free machine-translation providers sit behind it, asked in order and stopping at the first that answers — one that returns a ranked list of alternatives, then one on a different host that returns a single string, then a different vendor that also returns a single string.

The ordering rule is the whole design. Several alternatives inside one Target language is a hard requirement (ADR-0003), so a provider that returns a single string can never be a primary and is never reached while a ranked provider is available. Each hop is asked only when the one before it returned nothing, so a reader whose headword Wiktionary covers costs the chain no request at all, and a reader whose headword it does not costs one.

## The first hop could not answer until #20

The paragraph above was written on an assumption that turned out to be false: that a ranked provider absorbs most of the traffic. It absorbed none of it. The provider wraps its dictionary block in a one-element array, so the alternatives are at `body[5][0][2]`, and the parser read `body[5][2]` — the headword, a second time, rather than a list. An empty result is indistinguishable from a provider with nothing to offer, so every Lookup that reached the chain was sent on to a single-string hop that this ADR says must never be reached while a ranked one is available. Nothing errored and nothing looked broken: the ordering was not bypassed by a provider declining, it was bypassed by the extension misreading a provider that had answered.

Measured either side of the fix, on the same twelve Lookups — six headwords each into Bangla and Spanish, drawn from the shapes the opening paragraph names — the chain ran for eight of the twelve, and answered like this. Before: none at the first hop, four at the second, and four that were put to the third and produced no Translation at all. After: all eight at the first hop, none reaching the second or the third, and all eight producing a Translation, three of them with the several alternatives that made the ordering worth having. Those same eight Lookups put twenty-four requests into undocumented endpoints before the fix and eight after, the difference being the downstream asking that bought nothing.

The other four of the twelve never reached the chain at all: Wiktionary carried the equivalents, and no provider behind it was asked.

## The risk, accepted knowingly

All three endpoints are undocumented and their terms prohibit automated access. ADR-0004 already accepts this for the Google one, which Chrome's own Dictionary feature uses; this ADR extends the same acceptance to the other two vendors. The reasoning is unchanged and is worth restating rather than inheriting silently: these are consumer services with no key and no keyless contract, the extension needs no account and no credential, the request carries one headword, and the fallback is only reached for headwords a curated encyclopaedia does not cover. Enforcement is unlikely and the alternative is no Translation Field at all. The cost, stated plainly: a provider can begin refusing WordGlance outright, can change the shape of its answer without notice, and can serve a challenge instead of an answer — none of which this extension can fix. Each of those outcomes costs the reader the Translation Field and nothing else, which is what the chain exists to arrange. That clause was an assumption until the measurement above: half of the chain Lookups before the fix ended with an empty Field, which is the outcome it describes, and none do now.

## What the fix did to this risk

The acceptance above stands, and so does every part of its reasoning that does not depend on the split. What the fix changed is where the exposure sits: smaller in one direction, more concentrated in another.

Smaller, because the chain only runs where Wiktionary has no equivalent, so the number of readers whose word reaches a vendor whose terms prohibit automated access never depended on which hop answered. The same eight Lookups put the same eight requests into the first vendor either side of the fix; what the fix removed was the sixteen that went to the second and third vendors because the first vendor's answer could not be read. Total automated traffic into prohibited endpoints fell by two thirds.

More concentrated, because the traffic that reached the second and third vendors now reaches only the first. The chain still asks all three in order and the code has not changed — a headword the first provider holds no dictionary entry for goes to the second, as it always did, and none of the twelve here happened to be one. For a headword the first provider does answer, nothing behind it is asked, and that is the design working. It also leaves the case for three resting on a path that no Lookup in this measurement walked: two have to be down before the Field goes empty, and the two behind the first are covered per headword in the suite and by nothing live. The design guarantees they cannot be until the first hop stops answering, which is the point at which a reader finds out whether they are any use.

The load also moved onto the one vendor whose exposure was accepted on the record before any of this shipped. ADR-0004 accepts Google's unofficial endpoint on the grounds that Chrome's Dictionary feature uses the same one, and that acceptance was written for a provider that never ran, so until the fix it described a risk nobody was carrying. MyMemory and Bing had no standing of their own beyond the extension this ADR grants them, and are now asked only when the first provider has nothing for the headword.

So the position is the same exposure accepted for the same reasons, carried by the vendor whose acceptance is oldest, with a measurably better outcome for the reader. What changed is how many vendors a reader's word has to get through: one where before it was up to three. That is a reader-visible gain and a project-side loss in the same move, and neither is visible in the other. If `clients5.google.com` stops answering — a refusal, a challenge page, a shape the parser cannot read — the reader loses the Translation Field and nothing else, which is what this chain already does for a reader whose word nothing covers. The two hops behind it stay behind it rather than the extension moving a reader's word to whichever prohibited vendor still answers: losing the Field is the cheaper failure and the one already designed for.

The exposure is the author's, as ADR-0004 records it as a legal risk the author carries, and the decision is the author's. What would reopen it is Google withdrawing the endpoint deliberately, and the answer then is to say so in the store listing and in this ADR, not to substitute a different undocumented vendor quietly.

## What each hop is asked, and what failure costs

A hop that fails — a refused request, a server error, a body the extension cannot read, a challenge page, a headword the provider has no word for — is the next hop being asked. A chain that comes up empty is reported as not-found rather than as a connection error, because nothing the reader can act on has failed: the Field is empty, the Definitions they came for stay on screen, and telling them the network is down when it is up is the worse mistake of the two.

The Wiktionary request's own failure is deliberately not part of the chain. A request that errors or comes back with a server status is still a connection error, and stops the Lookup there. Only Wiktionary answering — with a page that has no equivalent in the reader's Target language, or with no page at all — is the coverage gap the fallbacks exist to cover. A word has no equivalents and the request failed are different facts, and ADR-0003's distinction between them is load-bearing.

A word that comes back identical to the headword is dropped wherever it appears. A machine translator handed a Bengali word and asked for Bengali hands the word straight back, and showing a reader the word they selected as its own Translation is the one thing this Field must never do. The explicit Source-equals-Target setting is suppressed before any request, so this catches the case that setting cannot: a reader who left their Source language on automatic and selected a word already in their Target language. A word genuinely spelled the same in both languages is lost to the rule, and the Wiktionary page above is where such a word is answered instead.

An empty Translation is not cached. Three providers being down at the same moment is a fact about the moment rather than about the word, and remembering it would tell the reader their word has no Translation until the browser next starts — which is the very outage the chain exists to absorb. This is the same rule the Definition chain already follows by throwing its not-found rather than caching it. An answer the chain did get *is* cached, because a repeat Lookup of a word already translated should cost nothing.

No request carries a cookie. The third vendor's session token is scraped from a page of its own and is the whole of what that hop has; the extension asks for no credential of any kind, and a reader's session on somebody else's site does not travel with a word they selected. If that hop needs a cookie to answer, it is a hop that does not answer for us, which is why it is last.

## Why three, and not one

Two would be a coin flip between two providers, and a coin flip is a bad answer for a field that is either right or conspicuously wrong. Three vendors means two have to be down before the Field goes empty, and they are chosen so that the two most fragile are not both fragile in the same way: the first is a single GET that answers with a ranked list, the second is a single GET on a different host answering with one string, and the third is a different vendor again, which is asked last because it hands out a session token on a page of its own and will not answer at all without it. Each is given a shorter request budget than the primary, because a Lookup that is going to come up empty must not cost the reader ten seconds per hop to learn so.
